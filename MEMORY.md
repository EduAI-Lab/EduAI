# Working memory

- The Question Maker new-question URL uses `QuestionComposerPage` and `ComposerMetadataFields`; changes to the older add-question dialog do not affect that route.
- Course topics created from AI Tutor and Question Maker authoring controls are written through the Core-backed topic API, then selected in the current form.
- Question Maker's shared `Toaster` has a dismiss button, and its app-level placement is top-right so it does not cover the sticky save actions.
- RAG/AI source of truth: `docs/rag-ai/README.md` indexes current chat/RAG, embeddings, routing, vLLM, testing, performance, and development-server guidance; HELPME references in `FUTURE_WORK.md` describe potential upgrades, not shipped behavior.
- Deployment source of truth: `docs/DEPLOYMENT.md` is the index for local, s378, production, inference, backup, health, and rollback guidance; `infra/inference/cmps01.md`, `cmps02.md`, and `cmps03.md` are dated host snapshots and must be revalidated after infrastructure changes.
- The course-detail manager view's staff tab reads "TAs" in the UI (#1727) but keeps `value="staff"`, `showStaffTab`, `canManageStaff`, `staffError`/`staffSuccess`, the `StaffUser` type and the `staff-tab` PICT capability id — rename display strings only, or the tab desyncs from `tests/models/course-detail-manager-view.*`.
- Bulk enrollment (#1756): CSV import and self-enrollment links both route through `addEnrollment()` in `app/lib/courses/enrollments.server.ts` — never write `prisma.enrollment` directly or you skip the `canAddEnrollmentRole` rank check. `addEnrollment` does NOT audit and does NOT enforce the instructor floor: every route logs `ENROLLMENT_ADDED` itself (single-add, CSV import, link redemption), and the floor lives in `updateEnrollmentRole`/`deactivateEnrollment`. Route through it **and log at the route**. `SelfEnrollmentLink` deliberately has NO role column so a forwarded link cannot mint staff; do not add one. Its migration (`20260916120000_add_self_enrollment_link`) was hand-written, then verified against real Postgres: `migrate deploy` applies cleanly and `migrate diff` shows the table matching `schema.prisma` exactly.
- Postgres `btrim(x)` with one argument trims **U+0020 only**, so it is not an equivalent of JS `.trim()`, which strips every Unicode space (tab, newline, form feed, NBSP, BOM, U+2028/2029, ideographic space…). `[^[:space:]]` is not equivalent either — it excludes NBSP and BOM. Any predicate that must agree across SQL and JS should use the explicit class in `app/lib/materials/indexable-text.server.ts` (#1795). A unit test that mocks `$queryRaw` and asserts the SQL *string* cannot catch this class of drift; the two predicates have to be evaluated over the same rows in a real database, which is what `app/tests/integration/material-indexable-text.integration.test.ts` does.
- `extractionLeaseUntil` means "a worker is alive on this row", and that is only true because every embed holding it renews it through `withLeaseHeartbeat` (`app/lib/materials/extraction-job.server.ts`). Before that, a job slower than `EXTRACTION_LEASE_MS` (15 min) looked abandoned and could be reclaimed mid-flight, starting a second `replace: true` embed over a live one. Any new code that takes this lease and then does long work must heartbeat it, or it reintroduces the race — and note a #685 restore target and a #1749 retry are indistinguishable by column, so the sweeper cannot tell them apart by row shape.
- Topic analysis (#1624) is owed by **every** path that lands a `CourseMaterial` in READY, not just the upload path — it is keyed off the row being indexed and readable, and `recordTopicAnalysisJobs` only picks up READY rows, so the call has to come after the status write. `runMaterialExtraction` and `runMaterialReembed` (the #1749 retry and the sweeper's resume) both do it (#1795). The soft-delete **restore** path in `runMaterialExtraction` still does not — a restored #685 material reaches READY with no analysis. Any new path to READY must start it, or its materials are silently absent from the course's topics with nothing to signal it.
- `useCourseMaterials`' background poll re-reads **page 1**, so it can only settle rows that live there. Uploads are newest-first and so always on page 1, but a retried material (#1749) can be PROCESSING anywhere in the list, which is why the poll also re-reads watched rows by id via `GET /api/courses/:id/materials?ids=` (#1795). Never settle a mutation by calling `fetchMaterials()`: it sets `loading` and resets `nextCursor`, discarding every page pulled with `loadMore` — update the row in place (`mergeMaterial`) instead.
- #1840: `Course.instructorId` is the **course head**, not the instructor list. `updateCourse` no longer deactivates the sitting instructor when it changes (that was the silent-demotion bug); `deactivateEnrollment` hands the column to the longest-standing remaining active instructor when the primary is removed, so it never dangles. The course-detail loader returns `courseInstructors` (every active INSTRUCTOR enrollment, with `enrollmentId`/`isPrimary`/`platformRole`) instead of a platform-wide INSTRUCTOR user list, and the manager view's add/remove revalidate that loader rather than keeping a second client cache.
- The `/api/users` candidate mode (`?courseId=&exclude=`) is pinned per mode: `enrolled`/`ta` require exactly `role=STUDENT&isActive=true` at rank >= 2; `instructor` (#1840) requires exactly `role=ADMIN,UNIT_ADMIN,INSTRUCTOR&isActive=true` at rank >= 3, matching `requiredRankForEnrollmentRole("INSTRUCTOR")`. Widening the role list is a 400, not a silent narrowing — otherwise the picker becomes a platform user directory. `useStudentCandidates(courseId, exclude)` picks the role set from `CANDIDATE_ROLES`.
