# Chat History

Server-side chat persistence for `/api/chat`. Clients send only the newest message; server reconstructs context.

## Basic Workflow

### 1. First Request (no chatId)

```json
POST /api/chat
{
  "messages": [{ "id": "uuid-v4", "role": "user", "content": "Hello" }],
  "model": "gpt-4",
  "apiKeys": { ... }
}
```

Response includes `chatId` in JSON body.

### 2. Subsequent Requests (with chatId)

```json
POST /api/chat
{
  "chatId": "cuid-from-server",
  "messages": [{ "id": "new-uuid-v4", "role": "user", "content": "Follow-up" }],
  "model": "gpt-4",
  "apiKeys": { ... }
}
```

Send only the new user message. Server loads last 20 messages from DB, merges, deduplicates by `messageId`.

## ID Generation

| ID | Generated By | Format |
|----|--------------|--------|
| `chatId` | Server | CUID |
| `messageId` | Client | UUID v4 |

## Details

- **Context limit**: Last 20 messages sent to LLM
- **Deduplication**: Same `messageId` on retry is safely ignored
- **410 Gone**: Chat deleted or wrong user → discard `chatId`, start fresh
- **Streaming limitation**: Assistant message persistence only works for non-streaming (`"streaming": false`). Streaming responses persist user messages but not assistant replies.

## Authentication

All requests to `/api/chat` authenticate via session cookie. The legacy `x-api-key` / Better Auth API-key plugin and `proxyUser` proxy-delegation have been removed (#158). Extensions (AI Tutor, Question Maker) that previously used `proxyUser` now authenticate their users via shared session cookie forwarding (`getEduAiCookieForRequest`).
