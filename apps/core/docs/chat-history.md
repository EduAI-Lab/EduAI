# Chat History

Server-side chat persistence for `POST /api/chat` (`app/routes/api/chat.ts`).
Clients send only the newest message; the server reconstructs context from
the database.

## Basic Workflow

### 1. First Request (no chatId)

```json
POST /api/chat
{
  "messages": [{ "id": "uuid-v4", "role": "user", "content": "Hello" }],
  "model": "gpt-4"
}
```

Response includes `chatId` in the JSON body (or via the stream, for streaming
requests).

### 2. Subsequent Requests (with chatId)

```json
POST /api/chat
{
  "chatId": "cuid-from-server",
  "messages": [{ "id": "new-uuid-v4", "role": "user", "content": "Follow-up" }],
  "model": "gpt-4"
}
```

Send only the new user message. The server loads prior history from the DB
and merges in any message whose `id` it hasn't seen yet
(`mergeMessages`, `chat.ts`).

## ID Generation

| ID | Generated By | Format |
|----|--------------|--------|
| `chatId` | Server | CUID (`Chat.id` default in `prisma/schema.prisma`) |
| `messageId` | Client (convention) | UUID v4 — but if a client omits `id`, the server stamps one with `randomUUID()` rather than rejecting the message (`normalizeMessage`, `chat.ts`) |

## Context window and long-thread digest

- **Message-count window**: up to `CHAT_MAX_CONTEXT_MESSAGES` messages are
  loaded from the DB and tail-trimmed before reaching the model. Default
  **100**, floor 4, ceiling 200 (`resolveMaxContextMessages`,
  `app/lib/chat-rag.ts`). This replaced an older, smaller fixed window — do
  not assume "last 20 messages" from older references.
- The real bound on what reaches the model is the **token/char budget**
  (`resolveSessionCharBudgetForModel`), not the message count. Long threads
  that exceed the recent-tail window get a **synthetic digest** of older
  turns spliced in ahead of the verbatim recent tail, so old context is
  summarized rather than silently dropped (`app/lib/chat-rag.ts`, tuned via
  `DEFAULT_SESSION_RECENT_MESSAGES` / `DEFAULT_SESSION_DIGEST_MAX_CHARS` and
  their `*_CEILING` bounds).
- **Deduplication**: the same `messageId` sent again on a retry is safely
  ignored, not double-persisted.

## Chat lifecycle and errors

- **410 Gone** — returned when either:
  - the `chatId` doesn't resolve to a chat the acting user owns (deleted, or
    belongs to someone else): `{"error":"Chat not found","chatDeleted":true}`
  - the persisted chat's `chatbotType` doesn't match the request's chat mode
    (e.g. resuming a `LEARNING` chat with an `ADMIN`-mode request):
    `{"error":"Chatbot type mismatch","chatDeleted":true}`

  Either way, the client should discard `chatId` and start a new chat.
- **`ChatbotType`** (schema enum): `LEARNING | ADMIN | INSTRUCTOR`. Only
  `LEARNING`-mode chats are editable/resumable once saved — ADMIN and
  INSTRUCTOR chat rows are read-only history after creation
  (`app/lib/chat-history/server.ts`).
- **Course scoping**: `Chat.courseId` is a nullable FK. A mode that requires
  a course with none supplied returns `400 COURSE_REQUIRED`; continuing an
  existing chat with a different course than the one it was created with
  returns `409 COURSE_MISMATCH`.
- **`regenerateOnly`**: a request flag for in-place ADHD-Assist content
  regeneration. Always non-streaming, persists nothing, and requires an
  existing chat the caller owns.

## Assistant-reply persistence

Both streaming and non-streaming requests persist the assistant's reply, not
just the user's message — streaming completes the persistence in the
stream's `onFinish` callback, non-streaming persists before returning the
JSON response. There is no asymmetry between the two modes.

## Viewing other users' chat history

Reading a chat's history isn't limited to its owner. Owners and ADMIN can
always read; instructor/TA/unit-admin oversight of a student's course chat is
gated by a course policy key (`courseChatViewPolicyKey` /
`canViewCourseChats`, `app/lib/rbac/permissions.ts`) and only applies to
chats owned by an actively-enrolled STUDENT.

## Rate limiting

`/api/chat` is throttled per user via `checkRateLimit("chat:<userId>", ...)`
(`app/lib/auth/rate-limit.server.ts`), configured by `CHAT_RATE_LIMIT` /
`CHAT_RATE_LIMIT_WINDOW_MS` (default 100 requests / 60000ms; the window var
falls back to the legacy `CHAT_RATE_WINDOW_MS` name if unset). Exceeding it
returns `429 RATE_LIMITED` with a `Retry-After` header.

## Authentication

Requests to `/api/chat` authenticate via one of three mechanisms:

- **Session cookie** — the normal path for browser clients.
- **`x-api-key`** — a Better Auth API-key plugin header, restricted to
  **ADMIN** users only (`enforceAdminIfApiKey`,
  `app/lib/auth/guards.server.ts`); non-admin callers get 403. Documented for
  end users on the API keys settings page.
- **`proxyUser`** — lets an admin-API-key-authenticated caller act on behalf
  of an external identity (`provider` + `externalUserId`), auto-provisioning
  a least-privilege STUDENT account on first use
  (`resolveProxyUser`, `chat.ts`). Only usable when the request already
  carries a valid admin API-key session; otherwise 403. This is how
  extensions delegate end-user identity into Core.

Extensions (AI Tutor, Question Maker) authenticate their own users to Core
via `POST /api/sessions/validate`, which requires a service key
(`Authorization: Bearer $EDUAI_API_KEY`) plus the forwarded end-user session
cookie — see [`DEPLOYMENT.md`](./DEPLOYMENT.md#extension-session-validation).
