## Admin

Walked in a real Chromium session against the `docker-compose.e2e.yml` stack (Core 3000 + AI Tutor 3001/4000), signed in as a freshly created platform `ADMIN`. Every row has a committed Playwright spec under `tests/e2e/tests/ai-tutor/` (8 admin spec files, 105 tests; the whole `ai-tutor` e2e suite is green at 161 tests, run serially with `--workers=1` as CI does).

Ten findings were recorded below and **all ten are now resolved** — nine were fixed, and BUG-3 turned out to be a defect in its own test rather than in the app. Every spec that used to pin the broken behaviour now asserts the fixed behaviour, so each fix carries a regression test.

**Status legend:** `Claude-tested` = paths found and walked through the browser, e2e test committed and green. A human pass is still required (README step 5) before any row counts as done.

**Scope note.** An AI Tutor admin is deliberately not a user-management *surface* — `nav.ts` and `routes/admin.js` both say users, roles, and enrollments belong to EduAI Core. That is true of the UI and **not** true of the API: the server still exposes a Core user roster and a full course-enrolment CRUD to ADMIN (`GET/POST/DELETE/PATCH /admin/courses/:id/enrollments`, `POST /admin/courses/:id/sync-enrollments`, `GET /admin/users`). Those paths are covered in [`admin-api-surface.spec.ts`](../../tests/e2e/tests/ai-tutor/admin-api-surface.spec.ts) because no screen reaches them and a human pass cannot walk them. The admin's own AI paths are configuration and oversight, not tutoring — an admin cannot open a tutoring chat, because `/student/*` is `STUDENT`/`TA` only.

### Findings — all fixed

All ten are resolved: nine were real defects and are fixed, and BUG-3 turned out
to be a defect in its own test rather than in the app. Every spec that used to
pin the broken behaviour (`test.fail`, or an assertion on the broken output) now
asserts the fixed behaviour, so each fix carries a regression test rather than a
note. No GitHub issues were filed — the fixes landed with the report.

- **BUG-1 — a grade could not be undone. Fixed.** `CourseSubmissionsPanel` omitted `isCorrect` when the result was "Not graded" and `score` when blank, so Save posted `{}` and `PATCH /activities/:id/submissions/:id` answered `400 {"error":"Nothing to update"}` behind a generic "Could not save the grade." The body is now built by `buildGradePayload`, which always sends both fields with `null` meaning "clear it" (the route already accepted an explicit null), and refuses a non-numeric score instead of silently dropping it. Unit test: `app/tests/unit/CourseSubmissionsPanel.grade-payload.test.ts`.
- **BUG-2 — Analytics → Student metrics printed raw user ids. Fixed.** `GET /courses/:id/student-metrics` now resolves Core display names exactly the way the submissions route does (`listEduAiCourseEnrollmentsServiceKey`, best-effort, degrading to the id when Core is unreachable), and the table renders the name. Integration tests cover the resolved name, an unknown id, and the Core-down path.
- **BUG-3 — not a bug; the test was wrong.** The claim was that activating a module/lesson card's "More options" kebab navigates into the card instead of opening the menu. What actually happened: the card itself has `role="button"`, and its accessible name was *computed from its contents* — the kebab's "More options" label included. `page.getByRole("button", { name: "More options" }).first()` therefore matched the **card**, and clicking a card navigates. Driving the real trigger (`button[aria-label="More options"]`) opens the menu with the page staying put. Publish, unpublish, edit, delete and "Move to position…" were reachable the whole time, and so was a module's description via the edit dialog.

  The nested-name problem was real, though — a screen reader announced the card as "01 Module Draft More options …" — so `ModuleCard` and `LessonCard` now carry an explicit `aria-label` ("Module: {title}" / "Lesson: {title}"). That fixes the announcement and makes the by-role selector unambiguous.
- **BUG-4 — the EduAI key-source badge went stale. Fixed.** The badge is rendered from the route loader, which is never revalidated, so it kept reading "From .env" after a save. `AdminSettingsPanel` now reports status changes up via `onStatusChange` and `admin.tsx` holds the badge state, so it follows both a save and a clear without a reload.
- **BUG-5 — the empty-topics guidance named a control that does not exist. Fixed.** The hint said "Open the course page and use **Sync topics from EduAI Core**, then try again"; AI Tutor has no such control: `CourseTopicsHeroAction` renders nothing for Core-linked courses, which is all of them since #1072, and the one sync endpoint that still exists (`POST /courses/:id/topics/sync`) is deprecated, UI-less, and would pull the same empty list the read path already auto-syncs. Topics are Core-owned, so the hint now reads "No topics on this course yet. Add some on EduAI Core, then try again." — which is the actual route out of the dead end.
- **BUG-6 — unknown/invalid ids fell through to a bare error boundary. Fixed, then generalised into one 404 page.** Every route under `_app.tsx` now exports a route-level `ErrorBoundary` (`RouteErrorState`), which renders *inside* the app shell — a boundary on the layout itself would take the shell down with it. `http()` throws `ApiHttpError` so the status survives to the boundary, and 404/400/403 all render one generic `NotFoundState` ("404 — Page not found"); only a genuine failure gets the separate "could not be loaded" state.

  That pulled in two neighbouring cases, so all three now answer identically: a URL matching no route (new catch-all `*` route, previously the root boundary's bare "404 / The requested page could not be found"), a route whose record doesn't exist, and a route this role may not open (previously a **silent redirect to `/`** — the reader asked for one page, got another, and was told nothing). `requireClientUser` throws a 404 on a role mismatch instead of bouncing, and a 403 from the API renders as not-found, so the app never confirms that a page exists to someone who cannot open it. Signing in is the one case that still redirects, which is correct: an unauthenticated reader has a way in.
- **BUG-7 — every AI Tutor bug report was stored with no type. Fixed.** `postCoreBugReport` rebuilt the Core payload field by field and dropped `bugType`, so every `source = AI_TUTOR` row landed with `bugType = NULL`, the triage Type column was always blank and its Type filter could never match. The forwarder now sends it. The related copy drift is gone too: `bug-report-dialog.tsx` builds its options from the same `BUG_TYPE_LABELS` map the triage table renders, so both surfaces say "UI / display" and "Performance".
- **BUG-8 — a manual grade override never reached Analytics. Fixed.** `ActivityStudentMetric` counters were only ever incremented, at submit time, so an override left Analytics reading Accuracy 0% while Submissions read 100% for the same course. `PATCH /activities/:id/submissions/:id` now calls `resyncSubmissionMetrics`, which re-derives that student's counters from their `Submission` rows and recomputes the aggregate — self-healing any earlier drift rather than nudging a counter.
- **BUG-9 — AI Tutor accepted an enrolment Core had never heard of. Fixed.** `POST /admin/courses/:id/enrollments` upserted the local `CourseEnrollment` without telling Core, while `PATCH .../role` refuses unless a Core enrolment exists — so an admin could create course access Core's audit trail never recorded and then be unable to manage it. POST now writes through to Core first (`createCoreEnrollment`, treating Core's 409 as success so the upsert stays idempotent) and surfaces Core's status on failure.
- **BUG-10 — ADMIN was locked out of the prompt-template store. Fixed, and the original diagnosis was incomplete.** Two independent gates were refusing an admin, not one. The recorded gate — `routes/prompts.js` using `requireRole("INSTRUCTOR")`, a bare string rather than a list — is now `["INSTRUCTOR", "UNIT_ADMIN", "ADMIN"]`, which is what actually unblocked UNIT_ADMIN. ADMIN was *still* 403'd afterwards, by `app.js`'s app-wide path isolation ("Admins can only access admin endpoints", `isAllowedAdminPath`) — a deliberate rule that keeps an admin out of instructor-facing surfaces, and one nothing in the original write-up mentioned. `/prompts` is now on that allowlist: system prompts, temperature and topP are platform configuration of the same kind as the AI loop policy the admin already owns under `/admin`, so reaching them is not "acting as an instructor". Students are still refused by the role gate.

### UI/UX notes (not bugs, worth a design pass)

- **Help advertises two things an admin cannot do.** The "Using the AI tutor" topic describes the student chat (`/student/*` is blocked for ADMIN), and the suite-tools topic says to look for the "Take Tour" button, which `canAccessStudentTour` renders only for STUDENT/TA. `HelpTopic` already supports a `roles` filter — both are one-line fixes.
- ~~**The "at least one AI mode" guard uses a native `alert()`**, both in the add-activity dialog and in the per-activity panel.~~ **Fixed.** Both now render the refusal inline, under the "AI study buddy" box that owns the mode chips (`AI_MODE_REQUIRED` in `app/lib/activityForm.ts`), and clear it as soon as a mode is re-enabled. Inline rather than a toast on purpose: the message sits next to the control that caused it and stays put while the reader fixes it.
- **The Feedback tab's filters are raw "Activity ID" / "Student ID" boxes** with no way to look either id up from that page.
- **The empty model catalogue says only "No AI models are available yet"** without saying the catalogue comes from EduAI Core, so an admin has nowhere to go next.

### Coverage that is still human-pass-only

- **AI oversight against real traces.** Course options in the oversight filter are derived from the traces themselves (`uniqueCourseOptions`), and a trace requires a working model-provider key, which the e2e stack does not have. - `tests/e2e/ai-tutor-rbac.spec.ts` sits outside the configured `testDir` (`./tests`), so it never runs. ## Unit Admin

**Role model.** A unit admin is `UserRole.UNIT_ADMIN` plus a non-empty `authorizedUnits` (department codes). The platform role alone does nothing — every course-scoped gate resolves through `authorizedUnits`, so a unit admin with no units sees nothing. AI Tutor learns both from Core's `POST /api/sessions/validate`; it has no sign-in or session of its own.

**Shape of the role.** Unit admins use the *instructor* shell (`usesInstructorShell()`), not a distinct one: same `/instructor` course list, same course/module/lesson screens, same authoring actions (`canManageContent()` admits the `unit` access level). What differs is scope — courses in `authorizedUnits` only. There is no unit-admin-only screen: the admin console is ADMIN-only, and course *creation* is owned by EduAI Core and absent from AI Tutor for every role.

**Reachable destinations:** `/` (redirects to `/dashboard` via `routeForRole`), `/dashboard`, `/instructor`, `/instructor/courses/:id`, `/instructor/module/:id`, `/instructor/lesson/:id`, `/settings`, `/help`. Not reachable: `/admin`, and all four student routes — `/student`, `/student/courses/:id`, `/student/module/:id`, `/student/lesson/:id`.

> **Refusal contract on this branch.** Every refusal — wrong role for a route, wrong unit for a record, or a URL matching nothing — resolves to the same generic in-shell 404 (`NotFoundState`), with the sidebar and header still mounted. That sameness is the point: the app must never confirm a record exists to someone who cannot see it. Over HTTP the answer is different and specific (403 with a reason), because an API caller is not a reader being let down gently. **Earlier revisions of this section described `development`'s redirect-and-bare-"Oops!" behaviour instead; those rows have been corrected.**

### What this pass changed

Four things were wrong here, and all four are now fixed in code. They are called out because three of them had been written up as *correct* behaviour:

1. **"Publish it" did not publish.** The dashboard's "Needs attention" CTA only navigated to the course page. The row below used to read "Minor UX: the label over-promises", on the premise that AI Tutor exposes no course publish at all — but `PATCH /api/courses/:id/publish` exists, admits `UNIT_ADMIN` department-scoped, and proxies to Core. `api.publishCourse` was live client code with no caller. The panel now performs the write behind a confirm; the missing control, not the label, was the defect.
2. **The admin console admitted unit admins.** The row below used to call the missing sidebar entry a "UX gap: Admin console unreachable by navigation". The navigation was right and the route was wrong: `/admin` is platform administration, and it is now ADMIN-only. `getNavForUser()` and `routes/admin.tsx` finally agree.
3. **No guided tour.** Recorded below as "correctly not offered", on the reasoning that the two existing tours are written in the learner's voice. True of *those* tours, not of the role — a staff-voiced `unit-admin-orientation` tour now covers the dashboard rollup, the drafts panel, the quick actions and the course list.
4. **The topics 403 was real.** `ensureCourseTopicAccess` read only the local membership tables, so a unit admin was refused topics on a course in their own unit — which silently stripped the course hero's topic chips and blocked activity authoring outright, since the form will not save without a main topic. It now resolves staff through `isCourseAdmin`, the predicate every other course-scoped gate uses. Topic *creation* is untouched and stays Core-only for imported courses.

- **"Course publish state is owned by Core and is absent from AI Tutor for every role."** Half right. ### Not yet covered for this role

Recorded here so the gap-sweep has somewhere to start. The first group is new — this pass added behaviour, and behaviour that is only ever driven down its happy path is barely pinned at all.

**Gaps this pass opened**

- **Every failure path on the new publish control.** Only the success path is driven. Three branches are untouched: the write rejecting (`toast.error`, and the row must *stay* in the panel rather than optimistically vanishing); the `corePublishStale` branch (#225 SEAM-04 — Core accepts the write but the read-back fails, and the toast has to say so instead of claiming a confirmed publish); and cancelling the confirm, which must leave the course a draft. The stale branch needs Core made to fail mid-request, so it is likelier a server integration test than an e2e one.
- **Publishing from the compact rows.** The panel renders a hero plus up to four `others` rows, and each row carries its own publish control. Only the hero's is clicked. A fixture with two in-unit drafts would cover both, and would also prove the right course is published when more than one is on screen.
- **The rollup after a publish.** The row leaving the panel is asserted; the revalidation behind it is not. Published/Drafts tiles and the donut are served by `GET /me/dashboard-stats`, so they only move if `revalidator.revalidate()` actually re-ran the loader — otherwise the tiles quietly contradict the panel.
- **The panel's "All caught up" empty state** for this role — a unit whose courses are all published, with the truncation notice still disclosing the page bound beneath it.
- **`canPublishContent()` returning false.** The guard that hides both publish controls is currently unreachable: the only two dashboards that render this panel (INSTRUCTOR, UNIT_ADMIN) both satisfy it. Either dead defensive code or a TA-facing surface nobody built — worth resolving rather than leaving as a branch no test can reach.
- **The tour past step 2.** `unit-admin-orientation` is driven through its first two steps only. Uncovered: steps 3–5, the cross-route hop from `/dashboard` to `/instructor` (the one piece of tour machinery specific to this tour), Back as well as Continue, Finish writing `aitutor:tour:completed:unit-admin-orientation`, and restarting a tour that has already been completed.
- **Launching the tour from `/instructor` in a browser.** The start-step fix is pinned by unit tests (`tour-engine.test.ts`, `tour-storage.test.ts`) — including the invariant that every route the tour is *offered* on has a step of its own, so starting it can never navigate away. No e2e drives the launch-from-the-course-list path itself, nor the sidebar control still reading "Stop Tour" after the tour hops to `/instructor` on its own.
- **The tour on an empty unit.** The course-list step anchors on the list container, which renders whether or not the unit has courses — so it should survive an empty unit. Asserted nowhere, and this is exactly the class of bug `emptyTarget` exists for (#1572).

**Staff-writable endpoints with no UI**

The publish gap was found by noticing a live endpoint with no caller. The same sweep turns up two more, both on the topics router, both admitting `UNIT_ADMIN`:

- **`POST /courses/:id/topics/remap`** merges topics and **deletes** the ones left unused. It has no client caller, and — unlike the create route beside it — **no imported-course guard**. So a unit admin can consolidate away topics on a Core-imported course, which the create route refuses on the grounds that Core owns them. Either the guard belongs here too or the create route's rule is not the rule; the boundary test added this pass only proves an *out-of-unit* remap is refused, which says nothing about the in-unit case. **Resolve this before covering it.**
- **`POST /courses/:id/topics/sync`** forces the Core pull that `GET /topics` otherwise throttles. Also has no client caller, and is exercised nowhere for any role.

**Topic behaviour the fixed gate now exposes**

- **Secondary topics.** `AddActivityPanel` has a second picker (`secondaryTopicIds`) beside the main one. Only the main topic is driven, so multi-topic tagging is unproven for the role that could not tag anything at all until this pass.
- **The auto-sync TTL.** `GET /topics` pulls from Core at most once per course per `AUTO_SYNC_TTL_MS`, and the import performs the first pull — which is why the fixture seeds its topic *before* importing. A topic added in Core afterwards is invisible until the window expires. Nothing covers that window, in either direction.
- **Core outage during a topics read.** The read now resolves this role through `isCourseAdmin` → `authorizeLiveCoursePrincipal`, so an unreachable Core costs a unit admin their topic list — and with it, silently, their ability to save an activity. That coupling is new and untested.

**Pre-existing, still open**

- **AI tutoring chat itself.** `POST /activities/:id/{teach,guide,custom}` is student-only — a unit admin authoring an activity has no way to try the tutor on it. Worth a row once someone decides whether that is correct (it means staff cannot preview what students experience).
- **Grading a submission.** `canGradeSubmissions()` admits `unit`, but exercising it needs a student submission in the fixture; the Submissions tab is currently only walked empty.
- **AI oversight with real traces.** Moot for the UI now that the console is closed to this role, but `GET /admin/ai-traces` still admits it, and its `courseId` / `limit` filtering is only ever walked empty. Producing a trace needs a student to run a tutoring session first. Tied to the open decision on that endpoint.
- **Unpublishing a course.** `PATCH /courses/:id/unpublish` is exercised as a fixture teardown and across the unit boundary, but its *cascade* — every module and lesson forced back to draft in one transaction — is asserted nowhere for this role. That is the destructive half of the pair, and it has no UI either: the panel publishes but never unpublishes, so a unit admin who publishes a course by mistake has no way back inside AI Tutor.
- **Completing an import.** Both import flows are driven up to the point of copying — module import through its preview, lesson import to the open panel — but neither actually copies. The copy mutates the shared fixture course, so it needs its own throwaway destination course.
- **Activity edit / duplicate / move / remove**, and **module/lesson reorder and move-to-position** — the controls exist (`Edit activity`, `Duplicate activity`, `Move activity to position`, `Remove activity`) but are not yet driven. Activity *creation* now works for this role, so these finally have a reachable starting point.
- **Enrollment management.** `canManageEnrollments()` returns `true` for `UNIT_ADMIN` (`permissions.ts:64`) and `nav.ts` carries an `enrollments` nav key, yet no enrollment surface appears anywhere in this role's app — user management and enrollments are owned by Core. Either a dead permission to remove or a missing screen; not yet resolved either way.
- **Core outage behaviour, generally.** `authorizeLiveCoursePrincipal` degrades a unit admin's department scope to empty when Core is unreachable (503 / blacked-out lists), and `enforceLiveCoursePrincipal` answers `state: "unavailable"` with a 503 rather than a 403 — a distinction no test for this role makes. The visible half is `routes/home.tsx`'s "Authentication service unavailable" screen, also uncovered.
- **A unit admin with an empty `authorizedUnits`.** The role model says the platform role alone does nothing, so this user should see no courses anywhere — dashboard, list, palette, breadcrumb switcher. The fixture always provisions at least one unit, so the degenerate case that the whole scoping model rests on is never actually run.
- **More than one authorized unit.** `createUnitAdmin` defaults to a single unit and every spec takes the default, so nothing proves the scope is a *set* rather than one department — a gate that read `authorizedUnits[0]` would pass every test here.

### A note on running these

The e2e stack serves **prebuilt images**. A container that has been up for a while can be running app code older than the working tree, and specs will pass against that older code — this sweep initially "confirmed" behaviour that no longer exists in the source. Rebuild before trusting a run:

```bash
docker compose -f docker-compose.e2e.yml build e2e-eduai-app e2e-ai-tutor-server e2e-ai-tutor-app
docker compose -f docker-compose.e2e.yml up -d
```

`docker inspect <container> --format '{{.Created}}'` is **not** a reliable staleness check — it reports container creation, and cached layers keep the image timestamp recent too. Grep the built bundle inside the container for a string you know is new instead.

## TA

A **TA** is not a platform role: Core has no `UserRole.TA`, so a TA is a platform `STUDENT` carrying a per-course `EnrollmentRole.TA`, promoted to the effective client role `"TA"` only in `/api/me` (`authentication.js`). That promotion is global ("TA anywhere"), so any *course-scoped* capability must be re-derived from the per-course enrolment, never the effective role — the class of bug behind BUG-TA-1 and #1626. A TA holds two surfaces at once: the staff instructor shell for the course they assist (read-only Content + Submissions/Feedback/Analytics + grading) and the STUDENT learner surface they keep by enrolment. Only `/admin`, content authoring, enrolment management, and answer submission are refused.

**Status legend:** `Claude-tested` = paths found, walked in-browser, and pinned by a committed green e2e test. `Manually-tested` = a human (Ye) also walked the row (README step 5).

### Findings

- **BUG-TA-1 — a TA could not grade, and the whole activity-level staff surface 403'd. Fixed.** A course TA's *platform* role is `STUDENT` (Core has no `UserRole.TA`), so on routes other than `/api/me`, `req.user.role` reads `"STUDENT"`. The activity-level TA re-checks — `GET /activities/:id/submissions`, `GET /activities/:id/feedback`, and the grade override `PATCH /activities/:id/submissions/:id` — called `getLiveStudentEnrollment(res, course, authUser)` with no `expectedRole`, so it defaulted the live allow-list to `[authUser.role]` = `["STUDENT"]`. The caller's real Core enrolment role is `"TA"`, which is not in that set, so `.allowed` came back false and each endpoint 403'd — *before* the very `liveEnrollment.role !== "TA"` check the `if (isTa)` branch was written to make. The result: the Submissions tab and its Grade dialog rendered for a TA (the *course-level* list authorises correctly), but Save always failed. Fixed in `server/src/routes/activities.js` by passing `"TA"` as the expected enrolment role at all three `isTa` re-check sites. Regression tests: [`ta-grading.spec.ts`](../../tests/e2e/tests/ai-tutor/ta-grading.spec.ts) walks the override end-to-end through the UI, and [`ta-security.spec.ts`](../../tests/e2e/tests/ai-tutor/ta-security.spec.ts) pins the three endpoints at 200. No GitHub issue filed — the fix landed with the report, matching the Admin section's convention.
- **U-TA-1 — a TA's answer submission was an enabled-but-dead Submit button. Fixed** ([#1625](https://github.com/EduAI-Lab/EduAI/issues/1625)). The lesson player is a learner surface a TA keeps, but recording an attempt is a STUDENT-enrolment path (`POST /questions/:id/answer` is 403 for a TA). The player used to show the radios and an enabled Submit for a TA and swallow the 403 on click. Fixed in `app/components/lessons/LessonActivityView.tsx` — a `submitState` prop now withholds the answer inputs and Submit and shows a note ("Teaching assistants don't submit answers"); `student.lesson.tsx`'s `submit()` is guarded too. The capability is the caller's **per-course** enrollment role (resolved by the breadcrumb's `viewerEnrollmentRole`), **not** the global `/api/me` role — and it **fails closed**: while the role is unresolved (pending or a failed breadcrumb) Submit stays withheld with a "checking access" / "couldn't verify" note, because `/api/me` falls back to the base STUDENT role when Core course discovery fails and must never be trusted to grant a Submit the answer route then 403s (#1626). Regression: [`ta-learner-access.spec.ts`](../../tests/e2e/tests/ai-tutor/ta-learner-access.spec.ts), plus unit coverage in [`LessonActivityView.submit-state.test.tsx`](../../apps/extensions/ai-tutor/app/tests/unit/LessonActivityView.submit-state.test.tsx).
- **U-TA-2 — the per-activity "AI study buddy" config controls rendered for a TA but were dead. Fixed** ([#1625](https://github.com/EduAI-Lab/EduAI/issues/1625)). On `/instructor/lesson/:id` the edit/duplicate/remove affordances were correctly withheld behind the `canManageContent` PermissionGate, but the AI mode chips (Teach me / Guide me / Custom prompt), the custom-prompt editor, and the topic selects were *not* — so a TA saw interactive authoring controls whose every write 403'd (`PATCH /activities/:id` is `requireRole(INSTRUCTOR/UNIT_ADMIN/ADMIN)`). Fixed in `app/routes/instructor.lesson.tsx` by wrapping the AI study buddy + Topics authoring grid in `<PermissionGate allow={perms.canManageContent}>`; a TA now sees the read-only "Question details" card and the main-topic badge, no dead controls. Regression: [`ta-activity-config.spec.ts`](../../tests/e2e/tests/ai-tutor/ta-activity-config.spec.ts), with the server 403 backstop pinned in [`ta-security.spec.ts`](../../tests/e2e/tests/ai-tutor/ta-security.spec.ts).

- **Staff tabs render on a course where the TA is only a student. Open** ([#1644](https://github.com/EduAI-Lab/EduAI/issues/1644)). `getCourseDetailTabs` gates the Submissions/Feedback/Analytics tab set on the global effective role, not the per-course enrolment, so the tabs show (and 403 on load) on a course the TA is enrolled in only as a student. Cosmetic authorization-surface leak — the server stays correctly per-course scoped.
- **TA dashboard "Assigned courses" mixes assisted and enrolled-as-student courses. Open** ([#1644](https://github.com/EduAI-Lab/EduAI/issues/1644)). `DashboardTaView` renders the unfiltered `courses` prop under "Assigned courses", so a course the account is a *student* in is listed as one it's assigned to as staff.

### UI/UX notes (not bugs, worth a design pass)

- **The learner list is discoverable only by direct URL.** A TA's sidebar "Courses" points at the staff `/instructor` shell; the `/student` enrolled-course list — which a TA legitimately uses to open the tutoring surface — has no nav entry. A TA who wants to *learn* rather than *assist* has to know the URL.

### Findings

- **Student BYOK key is the only route to chat, not a fallback. Open** ([#1645](https://github.com/EduAI-Lab/EduAI/issues/1645)). The study buddy requires a personal provider key even when UBC-hosted inference is available; a BYOK key also never populates the model picker (chat blocks with "No AI models configured"); and there is no BYOK fallback when the vLLM fleet is down.
- **Study buddy chat history is never persisted. Open** ([#1646](https://github.com/EduAI-Lab/EduAI/issues/1646)). The stateless `/api/completion` mints no `chatId`, so `upsertChatSession` no-ops and the history panel is always empty after leaving and returning.
- **AI Tutor → Core `/api/completion` blocked cross-origin. Open** ([#1647](https://github.com/EduAI-Lab/EduAI/issues/1647)). The guidance call forwards the user cookie but no service key, so Core's mutation guard 403s it whenever AI Tutor and Core are not same-origin.
- **MCQ option stays red on a same-question retry. Open** ([#1644](https://github.com/EduAI-Lab/EduAI/issues/1644)). `result`/`wasCorrect` aren't cleared when the student re-picks after a wrong answer, so the new choice renders red before resubmitting.
- **Submit stays enabled after a correct answer. Open** ([#1644](https://github.com/EduAI-Lab/EduAI/issues/1644)). The disabled check omits `wasCorrect`, so a correct answer can be re-POSTed repeatedly.

### UI/UX notes (not bugs, worth a design pass)

None broke a workflow, so none is a filed bug — each is a source-grounded design/accessibility rough edge for a later pass, ranked by severity.

_Cross-cutting:_

- **The AI study buddy — the flagship student feature — is gated entirely on a *student-supplied* provider key.** `hasApiKey` in `StudentAiChat.tsx` is `apiKeysLoaded && Boolean(currentApiKey)`, and `currentApiKey` comes only from the browser-local BYOK store (`use-api-keys.ts` → `provider-keys.ts`, providers Gemini / OpenAI / OpenCode Go). There is no client path where an admin-managed EduAI key unlocks the composer, so a fresh student with no key of their own always sees "Connect an AI provider to start", and the empty-state copy tells them to go get a key from `aistudio.google.com` — a heavy ask for a student, and it never mentions their institution might provide access. This is worth an explicit product decision (is student chat BYOK-only by design?), because the whole admin AI-config surface — the EduAI key, the loop policy, the tutor allowlist — has no visible effect on a student who hasn't brought their own key. **Not walked with a live provider in this stack**, so whether the send→answer path then works is human-pass-only (see above).
- **MCQ choices announce to a screen reader as "Option A" / "Option B", not their text.** The interactive `AnswerOption` (`packages/ui/src/answer-option.tsx`) sets `aria-label={`Option ${letter}`}`, which overrides the visible choice; a non-sighted student hears the letter but not what they are selecting. The lesson player's whole answering flow rides on this component, so it is worth an a11y pass (append or drop the label so the choice text is announced).
- **The "Before we start" knowledge-level personalization is buried behind the chat.** The pre-chat modal (`showKnowledgeModal`) is only reachable via the chat's "Change knowledge level" pill, which itself only appears after a provider is connected and a level is first chosen from the in-thread chips. The step the modal's own copy frames as "before we start" therefore never actually fronts the experience — it is an edit affordance for a choice made elsewhere.

_High:_

- **U1 — Finishing a lesson is a silent dead end.** On the last activity `canNext` goes false (`student.lesson.tsx:276`) and, after a correct answer, options + Submit + "Guide me" all lock, so every forward affordance is dead and the only escape is the breadcrumb. There is no "lesson complete" screen, no "next lesson", no "back to module" — the reward for finishing is a frozen card.
- **U2 — "Guide me" is silently inert for a student with no provider key.** The flagship secondary CTA calls `sendGuidePrompt`, which switches to the Guide tab then `return`s if no key is set (`StudentAiChat.tsx:534`, `if (!getKey(provider)) return`) — but the chat panel already shows the "Connect an AI provider" state, so the click produces zero visible change and reads as broken.
- **U3 — Switching the model to a provider you have no key for blanks the whole chat.** `hasApiKey` is derived from the *selected model's* provider (`StudentAiChat.tsx:234–236`) and the conversation area is gated on it (`:790`), so choosing e.g. an OpenAI model while holding only a Gemini key flips the panel back to the empty "Connect a provider" state with no warning that a model switch needs a different key.

_Medium:_

- **U4 — Returning students always restart at Question 1.** `idx` initializes to `0` and resets to `0` whenever the loader returns a new activities array (`student.lesson.tsx:174`, reset ~`:218`); completion badges show but first-unanswered / scroll position is never restored, so re-opening a partly-done lesson re-walks answered questions.
- **U5 — Wrong-answer retry works but is unguided and shows a stale banner.** Options stay enabled after a wrong answer, so a student *can* re-pick and re-submit, but `result` clears only on navigation (`student.lesson.tsx:299`–`307`), so the red "Not quite. Keep going!" banner persists while they select a new option, and there is no explicit "Try again" (see the new lesson-player row).
- **U6 — Chat timeout/error messages offer no retry or resend.** Failures append a plain assistant bubble ("That took too long…", "AI study buddy not available right now…", `StudentAiChat.tsx:496`–`503`); the student must retype their prompt.
- **U7 — Chat-history rows are indistinguishable.** Each saved session renders only a mode badge + relative time, no title/topic/first-message preview (`StudentChatHistoryPanel.tsx:165`–`172`), so several "Guide · 1h ago" rows are impossible to tell apart and "restore" is a gamble.
- **U8 — Feedback prompt is repetitive inline friction.** After the first attempt on *each* activity a 1–5 difficulty + note card is injected into the answer card (`student.lesson.tsx:333`–`353`), pushing Next down and recurring per activity across the lesson.
- **U9 — Result feedback is not announced; no focus move on question change (a11y, distinct from the "Option A/B" note).** The "Correct!"/"Not quite" banner is a plain `<div>` with no `role="status"`/`aria-live`, and navigating Next changes the question with no focus management (`LessonActivityView.tsx:289`–`305`), so screen-reader / keyboard students don't hear grading results or know a new question loaded.
- **U10 — Course-list search feels frozen during the server round-trip.** Search is debounced and applied server-side (good), but only the pager is disabled while `navigation.state==="loading"` (`student.tsx:250`–`256`); the card grid shows stale results with no skeleton/spinner, so on a slow connection the list looks unresponsive to typing.

_Low:_

- **U11 — Two inconsistent knowledge-level pickers + mismatched copy.** Inline chips ask "How much do you already know about this?" (`knowledge-level-chips.tsx`); the modal asks "What's your knowledge level on this topic?", titled "Before we start" with a "Start guidance" button (`student.lesson.tsx:686`–`725`) — yet it's reached *after* chatting has begun and confirming only sets the level (`handleConfirmKnowledge`, `:475`–`481`), no guidance is actually started.
- **U12 — Suggested-prompt chips only fill the input, they don't send** (`StudentAiChat.tsx:579`–`587`); a student expecting a one-click send must then find Send.
- **U13 — After a correct answer "Guide me" is disabled with no reason, but "Submit answer" stays clickable** (`LessonActivityView.tsx:280` vs `:259`–`261`), so a correct answer can be re-submitted repeatedly.
- **U14 — Misconfigured-MCQ is a hard stop.** Renders "This question's options are misconfigured." with no submit path and no report affordance (`LessonActivityView.tsx:240`–`243`).
- **U15 — Mobile: the chat is a fixed block stacked far below the question.** The student scrolls past question + answer + (per-activity) feedback card to reach the tutor, and the aside's default `h-[700px]` fights the `h-[600px]` wrapper (`student.lesson.tsx:655`; `StudentAiChat.tsx:651`).

_Cross-cutting bright spots already handled:_ page-boundary activity-load failure surfaces a toast + retry (`student.lesson.tsx:250`–`257`); the history panel and model-load have real error+retry states; course-list search is debounced and length-clamped; paged panels carry truncation notices.

### Coverage caveats — specs that pass but under-verify their claim

These rows are green, but the fixture can't distinguish the behaviour the row credits from a weaker one. Worth tightening so the test actually *guards* the property it names.

- **`#1207` "Question N of M uses the lesson total, not the loaded slice."** The nav spec seeds only 2 activities, which fit on one page, so "1 of 2 / 2 of 2" is identical whether M is the lesson total or the loaded slice — the test would still pass if the regression came back. Tighten by seeding more activities than the page size so slice < total. (Source *is* correct: `activitiesTotal` = API `.total`.)
- **`#1208` "search is server-side across every enrolled course."** The search spec seeds 2 courses on one page; a client-side filter over the loaded page gives the same result, so the server-side property is not guarded. Tighten by matching a course that lives on a later page. (Source *is* correct: `student.tsx:38`–`39` passes `search` to the loader.)
- **Progress filter "across every enrolment."** Uses a single course — proves the `?progress=` param is honoured, not that it spans pages. (Source correct: `student.tsx:51`.)
- **Pagination clamp "carries the search/filter params through the redirect."** The spec asserts the redirect to `page=1` but sends no search/filter params, so the param-carrying half of the claim is untested.
- **Spoofed `body.userId` "recorded against the authenticated caller."** `student-security.spec.ts` asserts only `status 200`; a server that *did* trust `body.userId` would also 200. Tighten by reading back `GET /me/submissions` and asserting the attempt is the caller's. (Source correct: `activities.js:1172` uses `authUser.id`.)

### Test-suite notes

- The whole student slice runs serially (`--workers=1`) like CI. Each spec registers its own fresh student and seeds its own course spine (published course → published module → published lesson → MCQ activity, owned by a *different* instructor/admin and then enrolled), so no test depends on another's state.
